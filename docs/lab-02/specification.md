# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal

Lab 2 extends TokTickIT from the Lab 1 full-stack foundation into a Requester-facing ticketing MVP. A user can select a temporary Development Requester identity, create an IT support Ticket, receive an official Ticket Number, view only their own Tickets, search and filter them, open Ticket Detail, and manage permitted Attachments. The sprint also establishes reusable Zen Green UI, API, validation, responsive, and testing conventions for later TokTickIT features.

## 2. Stakeholder Request Interpretation

The IT department needs a professional Requester-facing workflow for submitting and tracking support requests. Because real authentication is not implemented until Lab 3, Lab 2 uses a temporary Development Requester selector to simulate different users and test ownership behavior. Ticket data, reference data, and attachment metadata must be stored in PostgreSQL, while all requester-specific operations must prevent one selected Requester from accessing another Requester's Ticket or Attachment.

## 3. Scope

### Included

- Development Requester Selection used only as a Lab 2 testing context.
- Active Development Requesters loaded from PostgreSQL.
- Change Requester behavior and requester-specific data reload.
- Create Ticket workflow.
- Backend-generated unique Ticket Number.
- Initial Ticket status of `New`.
- Categories and Related Systems loaded from PostgreSQL.
- Requested Priority selection.
- Ticket Summary and Description validation.
- My Tickets list for the selected Requester.
- Search, filtering, sorting, and pagination.
- Requester-owned Ticket Detail.
- Attachment upload, metadata display, download, and soft removal.
- Attachment validation and ownership rules.
- Loading, empty, no-results, validation, success, and safe failure states.
- Zen Green responsive UI for desktop, tablet, and mobile.
- Unit, API/integration, UI component, UI style, responsive, and E2E testing.

### Excluded

- Real login, logout, passwords, password hashing, sessions, tokens, or authentication.
- IT Staff and Administrator workflows.
- Ticket Owner assignment.
- IT Priority changes.
- Public Comments.
- Internal Notes.
- Actions Taken.
- Ticket status changes after initial creation.
- Resolution, closure, reopening, or cancellation.
- User and reference-data administration.

## 4. Functional Requirements

- **FR-01:** The system shall load active Development Requesters from PostgreSQL and allow the user to select one as the current Lab 2 testing identity.
- **FR-02:** The system shall allow the current Development Requester to be changed and shall reload requester-specific data after the selection changes.
- **FR-03:** The system shall allow the selected Development Requester to create a Ticket using Category and active Related System reference data.
- **FR-04:** The backend shall generate and return a unique official Ticket Number after successful Ticket creation.
- **FR-05:** The system shall save each new Ticket with the selected Development Requester as its owner/requester and with Current Status `New`.
- **FR-06:** The system shall display only Tickets belonging to the selected Development Requester in My Tickets.
- **FR-07:** My Tickets shall support search, filtering, sorting, and pagination according to the documented API contract.
- **FR-08:** The selected Development Requester shall be able to open the read-only Ticket Detail screen for a Ticket they own.
- **FR-09:** The system shall reject access to a Ticket belonging to a different Development Requester.
- **FR-10:** The selected Development Requester shall be able to add permitted Attachments to an owned Ticket.
- **FR-11:** The selected Development Requester shall be able to download an active permitted Attachment from an owned Ticket.
- **FR-12:** The selected Development Requester shall be able to soft-remove one of their permitted Attachments using the documented removal rules.
- **FR-13:** Removed Attachments shall retain required metadata but shall no longer be previewable or downloadable.
- **FR-14:** The UI shall provide clear loading, validation, success, empty, no-results, submitting, and safe failure states for the applicable workflows.
## 5. Business Rules

- **BR-01:** The official Ticket Number shall be generated by the backend and shall be unique.
- **BR-02:** Every newly created Ticket shall begin with Current Status `New`.
- **BR-03:** Lab 2 shall use a Development Requester selector instead of real authentication. The selected identity is for testing only.
- **BR-04:** Only active Development Requesters shall appear in the Development Requester selector.
- **BR-05:** A Development Requester must be selected before requester-specific screens can be used.
- **BR-06:** Changing the selected Development Requester shall clear or reload requester-specific screen data so that data from the previous Requester is not retained.
- **BR-07:** A Ticket shall belong to exactly one Development Requester.
- **BR-08:** The Requester associated with a Ticket shall be taken from the current selected Development Requester context and shall not be editable on the Create Ticket form.
- **BR-09:** A selected Development Requester shall only be able to list and view Tickets that belong to that Requester.
- **BR-10:** Direct access to a Ticket belonging to another Development Requester shall be rejected by the backend.
- **BR-11:** Ticket Summary and Description shall be required and trimmed before validation and persistence.
- **BR-12:** Category and Related System selections shall reference valid records loaded from PostgreSQL, and the Related System must be active.
- **BR-13:** Requested Priority shall be selected from the approved Lab 2 priority values defined in the engineering contract.
- **BR-14:** Duplicate Ticket submission shall be prevented while a create request is already in progress.
- **BR-15:** A recoverable Ticket-creation failure shall preserve the Requester's entered form values so the user can correct or retry the submission.
- **BR-16:** My Tickets shall return only Tickets belonging to the selected Development Requester.
- **BR-17:** Search, filtering, sorting, pagination, default ordering, secondary ordering, and invalid-query behavior shall follow the documented API contract.
- **BR-18:** When no Tickets exist for the selected Requester, the UI shall show an empty state.
- **BR-19:** When Tickets exist but the current search or filters match no records, the UI shall show a distinct no-results state.
- **BR-20:** Allowed Attachment types are JPG/JPEG, PNG, WEBP, and PDF only.
- **BR-21:** An Attachment shall not exceed 5 MB.
- **BR-22:** A Ticket shall have at most five active Attachments.
- **BR-23:** Attachment filenames shall be treated as user-supplied metadata and shall not be used directly as unsafe storage identifiers.
- **BR-24:** An Attachment may be added only to a Ticket owned by the selected Development Requester.
- **BR-25:** Attachment download shall be allowed only when the Attachment is active and the parent Ticket belongs to the selected Development Requester.
- **BR-26:** Attachment removal shall be implemented as soft removal.
- **BR-27:** A soft-removed Attachment shall retain required metadata but shall not be previewable or downloadable.
- **BR-28:** Soft removal shall require a removal reason.
- **BR-29:** Attachment upload or removal failure shall return a safe error and shall not expose internal server, database, or storage details.
- **BR-30:** If a Ticket is created successfully but an optional Attachment upload fails afterward, the Ticket shall remain created and the UI shall report the Attachment failure separately.
- **BR-31:** The Development Requester context used in Lab 2 shall be designed so it can later be replaced by real authenticated user identity in Lab 3 without changing Ticket ownership semantics.
- **BR-32:** When an Attachment is soft-removed, its PostgreSQL metadata shall be retained for audit purposes, while its binary object shall be deleted from SeaweedFS.
- **BR-33:** Ticket creation, Attachment addition, and Attachment soft removal shall create an append-only Ticket Event in the same transaction as the corresponding database change.
- **BR-34:** Ticket Events are append-only audit records and shall not be updated or deleted through normal Lab 2 application workflows.

- **BR-35:** Attachment removal shall record the removal timestamp, removal reason, and the Development Requester who performed the removal.

- **BR-36:** The backend shall generate Ticket Numbers safely so that concurrent Ticket creation requests cannot produce duplicate Ticket Numbers.
## 6. UI Specification Summary

The detailed UI contract is defined in `docs/lab-02/ui-spec.md`. All Lab 2 screens shall follow the Zen Green visual foundation and provide consistent responsive behavior across desktop, tablet, and mobile layouts.

The Requester-facing workflow consists of:

1. Development Requester Selection
2. Create Ticket
3. My Tickets
4. Ticket Detail and Attachment Management

The application shall clearly display the currently selected Development Requester and provide a Change Requester action. Requester-specific screens shall not display stale data from a previously selected Requester.

Forms shall use clear labels, required-field indicators, field-level validation messages, disabled/busy states during submission, and safe API-error feedback. Lists and detail views shall provide appropriate loading, empty, no-results, and failure states.

Ticket Detail information is read-only in Lab 2 except for the permitted Attachment actions.

## 7. Data Changes

Lab 2 extends the existing Lab 1 PostgreSQL schema rather than replacing it. The existing `Category` model and its four seeded records are preserved for compatibility with the completed Lab 1 increment.

### 7.1 Identifier Decision

The existing Lab 1 `Category` model uses an auto-incrementing integer primary key. Lab 2 shall preserve that identifier to avoid an unnecessary primary-key migration of completed Lab 1 functionality.

New primary entities introduced in Lab 2 shall use UUID identifiers. Foreign-key types shall match the identifiers of the referenced models.

### 7.2 Category

The existing `Category` model is retained.

Required data:

- Account and Access
- Hardware
- Software
- Network

Category names remain unique. The Lab 2 seed shall continue to create/update these records idempotently.

### 7.3 Development Requester

A Development Requester represents the temporary Requester identity used for Lab 2 testing.

Required data:

- UUID identifier
- display name
- unique email
- active/inactive flag
- created timestamp
- updated timestamp

At least four active Development Requesters and at least one inactive Development Requester shall be seeded. Only active records shall be returned for Requester selection.

### 7.4 Related System

A Related System represents the application, service, or environment associated with a support Ticket.

Required data:

- UUID identifier
- unique name
- active/inactive flag
- created timestamp
- updated timestamp

At least six realistic Related Systems shall be seeded. Only active Related Systems shall be available for new Ticket creation.

### 7.5 Ticket

A Ticket represents one IT support request.

Required data:

- UUID identifier
- unique backend-generated Ticket Number
- Requester foreign key
- Category foreign key
- Related System foreign key
- Summary
- Description
- Requested Priority
- Current Status
- created timestamp
- updated timestamp

A Ticket belongs to exactly one Development Requester, one Category, and one Related System.

Requested Priority values for Lab 2 are:

- Low
- Medium
- High
- Urgent

New Tickets always begin with Current Status `New`.

The official Ticket Number follows the system format `TKT-YYYY-NNNNN` and is generated by the backend rather than supplied by the client.

### 7.6 Attachment

An Attachment stores metadata for a file associated with a Ticket. Binary file content shall not be stored directly in PostgreSQL.

Required metadata:

- UUID identifier
- parent Ticket foreign key
- original filename
- stored object identifier/key
- MIME type
- file size in bytes
- uploaded timestamp
- soft-removal timestamp, nullable
- removal reason, nullable
- removed-by Development Requester foreign key, nullable

An Attachment is active while its soft-removal timestamp is null. Soft removal retains its metadata.

The Attachment binary shall be stored in SeaweedFS rather than PostgreSQL. When an Attachment is soft-removed, its metadata remains in PostgreSQL for audit purposes, but its stored binary object shall be deleted so it can no longer be previewed or downloaded.

### 7.7 Ticket Event
A Ticket Event is an append-only audit record for material actions performed on a Ticket. Lab 2 shall create Ticket Events for Ticket creation, Attachment addition, and Attachment soft removal. The Ticket Event and the corresponding material action shall be persisted transactionally so that the audit history remains consistent with the Ticket state.
Required data:

- UUID identifier
- parent Ticket foreign key
- event type
- actor Development Requester foreign key, nullable when the action is system-generated
- event timestamp
- event metadata/details needed to describe the action

### 7.8 Relationships and Integrity

- One Development Requester may own many Tickets.
- One Category may be referenced by many Tickets.
- One Related System may be referenced by many Tickets.
- One Ticket may have many Attachment records, but no more than five may be active at one time.
- Ticket Number shall have a unique database constraint.
- Development Requester email shall be unique.
- Category name and Related System name shall be unique.
- Foreign-key relationships shall enforce referential integrity.
- One Ticket may have many Ticket Event records, and Ticket Events are append-only.
- Ticket creation, Attachment addition, and Attachment soft removal shall persist the corresponding Ticket Event transactionally with the material action.

### 7.9 Indexing

The schema shall include indexes that support the expected Lab 2 access patterns, including:

- Tickets by Requester and creation time.
- Tickets by Requester and status.
- Tickets by Category.
- Tickets by Related System.
- Attachments by parent Ticket and soft-removal state.
- Ticket Events by parent Ticket and event timestamp.

Exact Prisma declarations and migration output shall be reviewed before implementation is accepted.

### 7.10 Create Ticket Field and Validation Decisions

The following Lab 2 validation limits are implementation decisions made for this sprint. Frontend validation is provided for usability, but the backend remains authoritative and repeats all required validation.

| Field | Required | Editable | Validation / Behavior |
|---|---|---|---|
| Ticket Number | No | No | Generated by the backend only after successful creation. |
| Ticket Date | No | No | Generated by the backend from the Ticket creation timestamp. |
| Requester | Yes | No | Populated from the currently selected Development Requester. |
| Category | Yes | Yes | Must reference a valid Category from PostgreSQL. |
| Related System | Yes | Yes | Must reference an active Related System from PostgreSQL. |
| Ticket Summary | Yes | Yes | Trim leading/trailing whitespace; 5-120 characters after trimming. |
| Requested Priority | Yes | Yes | Must be one of Low, Medium, High, or Urgent. No silent default is applied; the Requester must make a selection. |
| Description | Yes | Yes | Trim leading/trailing whitespace; 10-5000 characters after trimming. |
| Attachments | No | Yes | Optional. Each selected file must satisfy the applicable Attachment rules in BR-20 through BR-35. |
| Current Status | Yes | No | System-generated as `New` for every newly created Ticket. |

#### Validation Decisions

- Summary uses a maximum of 120 characters so it remains concise enough for My Tickets lists while still allowing a meaningful problem description.
- Description allows up to 5000 characters so the Requester can provide detailed troubleshooting context without accepting unbounded input.
- Whitespace-only Summary or Description values are treated as empty after trimming.
- Category and Related System identifiers are validated against valid database records, and the Related System must be active, rather than trusted from client-provided display text.
- Requested Priority must be explicitly selected to avoid creating Tickets with an accidental priority.
- Invalid frontend input displays field-level messages and does not call the create-Ticket API.
- Backend validation returns safe field-specific errors for invalid data even if frontend validation is bypassed.
- After a recoverable API failure, valid entered values and valid selected files remain visible where practical so the Requester can retry without re-entering the form.

## 8. API Contract Summary

The detailed REST API contract is defined in `docs/lab-02/api-spec.md`. Lab 2 APIs shall use the `/api/v1` base path and JSON request/response DTOs except where file upload or download requires multipart or binary content.

The API shall provide capabilities for:

- retrieving Categories;
- retrieving active Related Systems;
- retrieving active Development Requesters;
- creating a Ticket for the selected Development Requester;
- listing only the selected Development Requester's Tickets;
- searching, filtering, sorting, and paginating My Tickets;
- retrieving one owned Ticket and its Attachment metadata;
- uploading an Attachment to an owned Ticket;
- retrieving Attachment metadata;
- downloading an active Attachment;
- soft-removing an Attachment with a removal reason.

### 8.1 Requester Context

Because Lab 2 does not implement real authentication, requester-specific API operations shall receive the current Development Requester identifier using the mechanism defined in `api-spec.md`.

The backend shall treat this identifier only as the temporary Lab 2 testing context. It shall still enforce Ticket and Attachment ownership on every requester-specific operation.

Changing the selected Development Requester in the UI shall cause subsequent requester-specific requests to use the new Requester context.

### 8.2 API Validation and Errors

The backend is authoritative for validation and ownership enforcement.

The API shall:

- reject missing or malformed required data;
- reject inactive or unknown reference-data identifiers;
- reject access to Tickets not owned by the current Development Requester;
- reject Attachment operations on Tickets not owned by the current Development Requester;
- reject invalid Attachment type, size, or active-count limits;
- reject download or preview of soft-removed Attachments;
- validate search, filter, sort, and pagination parameters;
- return field-level validation information where appropriate;
- use appropriate HTTP status codes;
- return safe client-facing error messages;
- avoid exposing stack traces, database details, storage paths, or other internal implementation details.

### 8.3 API Response Design

API responses shall use explicit DTOs rather than exposing database or Prisma models directly.

Ticket responses shall expose only fields required by the Lab 2 Requester workflows. System-generated values such as Ticket Number, Current Status, and timestamps shall come from persisted backend data rather than client-supplied values.

List responses shall include the Ticket items and pagination metadata required by the documented My Tickets contract.
## 9. Acceptance Criteria

### Development Requester Context

- **AC-01:** Given active and inactive Development Requesters exist in PostgreSQL, when the Requester selector loads, then only active Requesters are available for selection.
- **AC-02:** Given no Development Requester has been selected, when the user enters the application, then requester-specific workflows remain unavailable until a Requester is selected.
- **AC-03:** Given Requester A is selected, when the user changes to Requester B, then the current Requester display updates and requester-specific data is reloaded without retaining Requester A's Ticket data.
- **AC-04:** Given the Requester API cannot be reached, when the selector loads, then the UI displays a safe failure state without exposing internal server details.

### Create Ticket

- **AC-05:** Given a valid Create Ticket submission, when the backend accepts the request, then exactly one Ticket is persisted with a unique backend-generated Ticket Number, Current Status `New`, the selected Development Requester as owner, and a corresponding Ticket-created Ticket Event.
- **AC-06:** Given the Create Ticket screen loads successfully, then Categories and active Related Systems are populated from PostgreSQL.
- **AC-07:** Given required input is missing or violates the documented validation limits, when the Requester attempts to submit, then field-level validation messages are shown and invalid data is not persisted.
- **AC-08:** Given Ticket creation is in progress, then the submit control shows a busy state and duplicate submission is prevented.
- **AC-09:** Given a recoverable Ticket-creation API failure occurs, then the UI displays a safe error and preserves the Requester's entered values for retry.
- **AC-10:** Given Ticket creation succeeds, then the UI displays the persisted Ticket Number, Requester, Ticket Date, Category, Related System, Requested Priority, Description, and Current Status.

### My Tickets

- **AC-11:** Given Requester A is selected, when My Tickets loads, then only Tickets belonging to Requester A are returned and displayed.
- **AC-12:** Given Requester A and Requester B own different Tickets, when the selected Requester changes from A to B, then A's Tickets disappear and only B's Tickets are shown.
- **AC-13:** Given Tickets exist, when a supported search term is entered, then My Tickets returns only matching Tickets according to `api-spec.md`.
- **AC-14:** Given Tickets exist, when supported filters are applied, then only Tickets matching those filters are returned.
- **AC-15:** Given Tickets exist, when a supported sort option is selected, then results are returned in the documented deterministic order.
- **AC-16:** Given more Tickets exist than fit on one page, when pagination is used, then the correct page is returned with the documented pagination metadata.
- **AC-17:** Given the selected Requester owns no Tickets, then My Tickets displays the empty state.
- **AC-18:** Given the selected Requester owns Tickets but the current search or filters match none, then My Tickets displays a distinct no-results state.
- **AC-19:** Given invalid list query parameters are supplied, then the API handles them according to `api-spec.md` and returns a safe response.

### Ticket Detail and Attachments

- **AC-20:** Given the selected Requester owns a Ticket, when Ticket Detail is opened, then the saved Ticket information and active Attachment metadata are displayed and Ticket fields are read-only.
- **AC-21:** Given the selected Requester does not own a Ticket, when that Ticket is requested directly, then the backend rejects access without returning the Ticket data.
- **AC-22:** Given the selected Requester owns the Ticket, when a permitted Attachment of 5 MB or less is uploaded while fewer than five active Attachments exist, then the Attachment is stored successfully, its metadata is persisted, and an Attachment-added Ticket Event is created.
- **AC-23:** Given an Attachment has an unsupported type, exceeds 5 MB, or would exceed five active Attachments, when upload is attempted, then the upload is rejected with a safe error.
- **AC-24:** Given an active Attachment belongs to an owned Ticket, when download is requested, then the authorized file is returned.
- **AC-25:** Given the selected Requester owns an active Attachment, when a valid removal reason is submitted, then the Attachment is soft-removed, its removal timestamp, reason, and removing Development Requester are recorded, its binary object is deleted from SeaweedFS, and an Attachment-removed Ticket Event is created.
- **AC-26:** Given an Attachment has been soft-removed, when preview or download is requested, then access is rejected.
- **AC-27:** Given an Attachment belongs to another Requester's Ticket, when metadata, download, or removal is requested, then the backend rejects access without exposing the Attachment.
- **AC-28:** Given Ticket creation succeeds but an optional Attachment upload fails afterward, then the Ticket remains created and the UI reports the Attachment failure separately.

### UI and Responsive Behavior

- **AC-29:** Given any Lab 2 Requester screen is displayed, then the UI follows the documented Zen Green design foundation and shared component rules in `ui-spec.md`.
- **AC-30:** Given the application is viewed at the documented desktop, tablet, and mobile widths, then the required workflows remain usable without unintended horizontal page scrolling.
- **AC-31:** Given a workflow is loading, empty, submitting, successful, invalid, has no results, or encounters an API failure, then the applicable documented UI state is clearly presented to the user.

## 10. Definition of Done

A Lab 2 feature is Done only when:

- its behavior follows this specification and the approved `api-spec.md` and `ui-spec.md`;
- applicable acceptance criteria are implemented;
- database migrations and seed behavior are repeatable;
- backend validation and Requester ownership enforcement are implemented;
- frontend validation and required UI states are implemented;
- applicable unit, API/integration, UI, responsive, and E2E tests pass;
- the AC-to-test traceability in `tests.md` is updated;
- no Lab 3 functionality has been introduced;
- implementation changes have been reviewed through the required feature-branch and Pull Request workflow;
- required grading evidence has been captured.
- required Ticket Events are created transactionally for Ticket creation, Attachment addition, and Attachment soft removal;
- Attachment binaries are stored in SeaweedFS rather than PostgreSQL, and soft removal retains metadata while deleting the binary object;
- Ticket Number generation remains unique and safe under concurrent creation requests;

## 11. Assumptions and Engineering Decisions

- **AD-01:** The Development Requester selector is a temporary Lab 2 testing mechanism, not authentication.
- **AD-02:** Existing Lab 1 Category integer identifiers are preserved; new Lab 2 primary entities use UUIDs.
- **AD-03:** Ticket Number format follows the approved system-level format `TKT-YYYY-NNNNN`.
- **AD-04:** Summary length is 5-120 trimmed characters and Description length is 10-5000 trimmed characters.
- **AD-05:** Requested Priority requires an explicit Requester selection from Low, Medium, High, or Urgent.
- **AD-06:** Ticket creation and optional Attachment upload are treated as separable operations so an Attachment-storage failure does not delete an otherwise valid created Ticket.
- **AD-07:** Exact My Tickets search fields, filters, sorting options, pagination defaults, and invalid-query behavior are defined in `api-spec.md`.
- **AD-08:** Exact attachment storage, upload, download, and removal request/response behavior is defined in `api-spec.md`.
- **AD-09:** Detailed visual tokens, components, responsive breakpoints, and UI states are defined in `ui-spec.md`.
- **AD-10:** Every acceptance criterion in this document must map to at least one planned automated or documented verification in `tests.md`.
